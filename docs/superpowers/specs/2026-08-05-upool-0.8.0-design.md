# U-Pool 0.8.0 — design

Status: implemented 2026-08-06. Written before the code, so section 6 began as a
*measurement to perform*; it has since been taken and now records what was found.
Sections 3 and 4 have been updated to what the live endpoints and the live
database actually contained, and where that differs from what was designed, the
difference is called out rather than smoothed over.

**Section 11 is the correction that running it against a real machine forced.**
The premise "a pasted browser cookie is the account's key" is half true: the
cookie reads the account (name, plan, usage) but does not sign the desktop app
in. Read it first before section 5's `use()`.

## 11. The credential is two kinds of token, and only one switches

Measured, not reasoned. A cookie exported from a browser and a session taken from
a signed-in desktop Cursor were compared claim by claim:

| | Browser cookie | Desktop session |
|---|---|---|
| JWT `type` claim | `web` | `session` |
| `workosSessionId` | present | absent |
| Authenticates the cursor.com API (`/api/auth/me`, usage, plan) | **yes** | yes |
| Signs the desktop client in when written to `state.vscdb` | **no** | yes |

Writing a `web` token into `state.vscdb` does not fail quietly - Cursor validates
it on launch, rejects it, and **signs itself out**, leaving `accessToken` absent
and `glass.lastSignedInAuthId` = `signed-out`. Confirmed on the author's machine:
a switch to a pasted-cookie account logged the user out; writing back a real
session token logged them straight back in.

### What ships in 0.8.0

`switch.use()` reads the token kind off the JWT (`upool.cursor.models.token_kind`)
and **refuses a `web` token** with a message that says why, rather than writing it
and signing the editor out. The card disables Use on a browser-cookie row and
carries `token_kind` in its summary - never the token - so the UI can explain it.

So what actually switches in 0.8.0 is a **session** token, and the pool already
captures those: `_adopt_live_session` banks the session of whoever is signed into
the desktop app, and a session token pasted by hand (exported from a logged-in
`state.vscdb`) is accepted too. A browser cookie is display-only: it fills a card
with usage and plan, and Use is disabled on it.

### The exchange, proven and deferred

A `web` cookie **can** be turned into a `session` token - Cursor's own deep-login
flow does it, and it was reproduced end to end for one of the author's accounts:

```
web cookie  ->  GET  cursor.com/loginDeepControl?challenge&uuid&mode=login   (cookie authorises)
            ->  POST cursor.com/api/auth/loginDeepCallbackControl {uuid, challenge}
            ->  GET  api2.cursor.sh/auth/poll?uuid&verifier   ->  {accessToken (session), refreshToken}
            ->  write to state.vscdb  ->  desktop signs in as that account
```

Verified by minting a session token from a browser cookie and signing the desktop
in as a *different* account with it. The confirm step needs a WorkOS AuthKit
session, which a browser establishes natively; a pure-HTTP replay stalls on the
AuthKit login page, so a robust implementation embeds a controlled webview that
injects the cookie and drives the confirm. That is real work with a live keystone
risk (httpOnly cookie injection in pywebview / WebView2) and ongoing fragility as
Cursor's auth changes. Deferred rather than rushed into 0.8.0; the refusal above
is what keeps 0.8.0 honest until it lands.

## Why

Cursor is the one AI tool on this machine U-Pool cannot switch, and it is the one
where switching is hardest by hand: an account lives in a SQLite database the
editor holds open, so changing it means quitting Cursor, editing a binary file,
and starting it again. People keep several Cursor accounts and currently rotate
them by signing out and in through a browser, which loses the previous session
entirely - there is no pool to come back to.

The reference implementation, `6639835/cursor-account-switcher`, does this as a
Tauri app: accounts in a CSV, `WorkosCursorSessionToken` as the credential,
switching by closing Cursor, resetting the machine ID and rewriting
`state.vscdb`. U-Pool already owns the "pool of credentials, one live at a time"
shape for five other tools; Cursor is the sixth.

Token usage tracking for Claude Code and Codex was considered for this release
and cut - see section 10.

## 0. Why this is not an adapter

A Cursor account is not a `Provider`. It has no `base_url`, no `api_key`, no
`model`, no `auth_style`; it has a session cookie, a plan, and a usage figure
that comes from the network rather than from the record. Putting it in
`SUPPORTED_APPS` would mean `validate()` demanding a request URL for something
that has none, half the provider form rendering fields with no meaning, and six
exhaustive `Record<AppId, …>` maps in the UI carrying an entry that lies.

So Cursor gets its own package, its own file and its own list component, and the
existing five apps are not touched at all. What it *does* borrow is
`adapters.base.ApplyResult`: a switch reports files written, backups taken and
warnings raised in exactly the shape the UI already renders, so the toast after a
Cursor switch is the same toast as after a Claude switch.

In the UI this is a `TabId = AppId | "cursor"` union. The `Record<AppId, …>` maps
stay exhaustive over provider apps only; nothing is widened to accommodate a tab
that does not behave like one.

## 1. `src/upool/cursor/` — layout

| Module | Owns | ~lines |
|--------|------|--------|
| `models.py` | `CursorAccount` | 80 |
| `parse.py` | text → accounts | 120 |
| `api.py` | cursor.com client | 180 |
| `vscdb.py` | `state.vscdb` read/write | 150 |
| `process.py` | is Cursor running / close it / start it | 100 |
| `store.py` | `~/.u-pool/cursor.json` | 150 |
| `switch.py` | the orchestration of a switch | 90 |

Seven small modules rather than one file, because four of them are independently
dangerous and each wants its own test file. `vscdb.py` in particular must be
readable in one sitting by anyone reviewing what U-Pool writes into a database
holding the user's entire Cursor history.

`CursorAccount` fields: `id`, `user_id`, `email`, `name`, `token`, `plan`,
`plan_status`, `usage_used`, `usage_limit`, `usage_unit` (`"usd"` /
`"requests"`), `usage_percent`, `status` (`"ok"` / `"expired"` / `"unknown"`),
`last_checked`, `added_at`.

There is no `period_end`. `/api/auth/stripe` returns one, and the card does not
show it - a field stored for a display that was considered and declined is a
field that goes stale without anyone noticing.

**`user_id` is identity, not `email`.** It is the half of the cookie before
`::`, it is available before any network call, and it is what makes a re-paste
of the same account refresh a row instead of duplicating it. An email is not
known until `/api/auth/me` answers, and on an expired token it never does.

## 2. Input parsing — `parse.py`

One entry point. The input is split into lines; each line is tried against the
forms below in order and the first that matches wins:

1. Netscape `cookies.txt` - seven tab-separated fields, credential in field 7
   where field 6 is a recognised cookie name
2. `WorkosCursorSessionToken=user_01AB%3A%3AeyJ...` - also
   `__Secure-next-auth.session-token` and `next-auth.session-token`, which
   cursor.com still accepts
3. A bare `user_01AB::eyJ...`, percent-encoded or not
4. `email,token` CSV, as the reference implementation exports
5. A JSON object or array with `token` / `accessToken` / `cookie` keys

A line that matches nothing is **skipped silently**. A `cookies.txt` exported
from a browser holds comment lines and every other domain's cookies; reporting
each one is noise in a 200-line paste. The result is a count -
`{added, refreshed, skipped}` - and that is what the toast says.

Bulk and single are the same code path and the same box: paste one line or two
hundred, or pick a `.txt` file whose contents go into the same parser. A
separate "bulk import" screen would be a second implementation of one function.

Duplicate `user_id` refreshes the stored token and leaves the rest of the record
alone, so re-pasting a rotated cookie for an account already in the pool keeps
its position, its name and its last-known usage.

## 3. cursor.com client — `api.py`

Stdlib `urllib` only, following `health.py`. No new dependency.

Header: `Cookie: WorkosCursorSessionToken={user_id}%3A%3A{token}`.

| Call | Read |
|------|------|
| `GET /api/auth/me` | `email`, `name` |
| `GET /api/auth/stripe` | plan name, subscription status |
| `GET /api/usage-summary` | current-period used / limit in USD, on-demand |
| `GET /api/usage?user={id}` | fallback: request counts and `maxRequestUsage` |

The fourth is the legacy request-based endpoint and is called **only** when
`usage-summary` returns nothing usable, which is what a request-quota plan does.

Measured 2026-08-06 against a live account, which corrected one thing the design
got wrong: `usage-summary` nests its figures **two levels down**, as
`individualUsage.plan.{used, limit, remaining, totalPercentUsed}`. The extractor
walked into `individualUsage` and stopped, so an account with real numbers
reported none and fell through to the legacy endpoint. The section list is a fixed
set of names rather than a walk of the whole document precisely because the
sibling `onDemand` block carries a different number under the same `used` key -
and `teamUsage` carries somebody else's. `/api/auth/stripe` answered with
`membershipType` and `subscriptionStatus`, which are the same two strings Cursor
stores in `state.vscdb`, so a plan round-trips exactly.

The three live bodies are recorded verbatim in `tests/test_cursor_api.py` as
`LIVE_SUMMARY`, `LIVE_STRIPE` and `LIVE_LEGACY` - the only fixtures in that file
that are evidence rather than argument.

These are the endpoints cursor.com's own dashboard calls. They are undocumented
and will change without notice, so every field is read as optional and a missing
one renders as `—`. **A shape change must degrade the card, never break the
switch** - the token is what switching needs, and the token does not come from
any of these calls.

- `401` → `status = "expired"`. The row stays, greyed, badged, with `Use`
  disabled. **`/api/auth/me` does not answer 401**, though: measured against a
  revoked cookie, a made-up one and no cookie at all, it answers `204` with an
  empty body, where a working cookie gets `200` and a body. Read as a malformed
  response - which is what an empty body looks like to a JSON parser - it would
  have left a signed-out account saying "could not refresh" forever. So 204 is a
  rejection on that one call and on no other; the other three keep to 401.
- **A rejected cookie is not asked twice.** Once any call has been rejected, the
  legacy usage endpoint is not tried. It sometimes answers anyway, and one
  endpoint answering is what marks an account healthy - so asking would revive a
  cookie cursor.com had just refused. It is not deleted: the record still carries the email and name, so
  pasting a fresh cookie revives it in place.
- A network or 5xx failure leaves `status` untouched and reports "could not
  refresh". A Cursor outage must not mark a working account dead.
- Partial success fills partially. `me` succeeding while `usage-summary` fails
  gives a card with a name, an email and a `—` usage bar.

Refresh follows the `clis` / `updater` pattern already in the codebase:
`bootstrap` returns the cache immediately and starts a `ThreadPoolExecutor` (8
workers) over every account; the UI polls while `busy`. First paint never waits
on the network, and cards fill in as answers arrive.

## 4. `state.vscdb` — `vscdb.py`

`%APPDATA%\Cursor\User\globalStorage\state.vscdb` on Windows,
`~/Library/Application Support/Cursor/...` on macOS, `~/.config/Cursor/...` on
Linux. Only the Windows path is exercised: like `autostart` and `winenv`, the
other two are resolved so the code is not Windows-shaped, not because they have
been tested. On the machine this was written for the database is 1.38 MB and
holds three tables: `ItemTable`, `cursorDiskKV` and `composerHeaders`. The
latter two are the user's conversations and composer state. `ItemTable` also
holds `mcpOAuth.secret.*` rows - live OAuth secrets for MCP servers.

This is the most dangerous write target U-Pool has ever had, and the ownership
doctrine applies to it without dilution:

- **Owned: eight named `ItemTable` keys, and nothing else.** Seven under
  `cursorAuth/` plus `glass.lastSignedInAuthId`; the list and the reason that last
  one widens this claim are in section 6. Ownership is by exact key, never by the
  `cursorAuth/` prefix - a prefix sweep would take whatever Cursor adds under it
  next, and `onboardingDate` is already an example of one that must not move.
- Writes are `INSERT OR REPLACE` on named keys. There is no `DELETE FROM
  ItemTable`, no `DROP`, no `VACUUM`, no rewrite of the file.
- `cursorDiskKV` and `composerHeaders` are never opened. Non-`cursorAuth`
  `ItemTable` rows are never read.
- `storage.json` (`telemetry.machineId`, `telemetry.devDeviceId`,
  `telemetry.sqmId`) and `%APPDATA%\Cursor\machineId` are **not touched**. The
  reference implementation resets them; that is not part of switching accounts,
  it is defeating a per-device limit, and those values are Cursor's own state
  rather than anything U-Pool wrote.
- The Electron cookie jar (`%APPDATA%\Cursor\Network\Cookies`, DPAPI + AES-GCM)
  is not written. Section 6 decides whether it even needs to be read.
- `_guard` refuses any target that does not resolve under `paths.cursor_app_dir()`,
  mirroring `sessions._guard`. Nothing the user types reaches this path, so it
  fires only on a resolution bug - which is exactly the failure that would make
  the write unbounded.
- `backup.sidecar()` runs first: `state.vscdb.backup` beside the original, so
  undoing a switch is one rename in a folder the user can already open.

The database is only written while Cursor is not running, so the `-wal` and
`-shm` files are in a settled state. Cursor holding the file open is the reason
the switch closes it first, not a lock the writer works around.

## 5. Switching — `process.py` + `switch.py`

```
Use pressed
  ├─ Cursor not running → back up → write → launch
  └─ Cursor running → modal: "Cursor will be closed. Continue?"
        └─ confirmed → polite close request (taskkill /IM, never /F)
              ├─ gone within 10s → back up → write → launch
              └─ still there → WRITE NOTHING
                    → "Cursor did not close - you may have unsaved changes.
                       Close it yourself and try again."
```

**No force kill.** A `/F` on an editor discards whatever it was holding, and the
account being switched to is worth less than an unsaved file. A switch that
sometimes says "do it yourself" is better than one that sometimes costs work.

**No partial write.** If the close fails, not one byte reaches `state.vscdb`.
The failure mode of a half-applied auth record is an editor that will not sign
in and cannot be signed out.

`switch.py` returns an `ApplyResult`, so files, backups and warnings surface
through the same UI path as every other switch.

## 6. The measurement — taken 2026-08-06

Snapshot signed out (100 `ItemTable` rows), sign in to Cursor 3.14.7, snapshot
again (148). **50 rows appeared and 18 changed.** Almost all of that is the
session rather than the account - window layout, the colour theme, 594 KB of
pushed experiment config, 56 KB of server config. These are the rows that are the
account:

| Key | Value on this machine | Owned |
|-----|----------------------|-------|
| `cursorAuth/accessToken` | 413-char session JWT | yes |
| `cursorAuth/refreshToken` | **byte-identical to the access token** | yes |
| `cursorAuth/cachedEmail` | `umutday11@gmail.com` | yes |
| `cursorAuth/cachedSignUpType` | `Auth_0` | yes |
| `cursorAuth/cachedScopedProfile` | `{"displayName":…,"pictureUrl":…}` | yes |
| `cursorAuth/stripeMembershipType` | `free` | yes |
| `cursorAuth/stripeSubscriptionStatus` | `unpaid` | yes |
| `glass.lastSignedInAuthId` | `auth0\|user_01JAXG…` | yes - see below |
| `cursorAuth/onboardingDate` | `2026-08-05T21:00:12.742Z` | **no** |

Four findings that changed the code:

1. **Values are stored raw, not JSON-encoded.** `cachedEmail` is
   `umutday11@gmail.com`, not `"umutday11@gmail.com"`. Only `cachedScopedProfile`
   is JSON, because it really is an object.
2. **`accessToken` and `refreshToken` hold the same string.** A pooled account has
   one credential, and that turns out to be exactly what Cursor keeps.
3. **The cookie jar is empty while signed in.** `%APPDATA%\Cursor\Network\Cookies`
   has zero rows. `state.vscdb` alone carries the session, so the jar is never
   opened - the open question at the end of the original section 6 is closed.
4. **Two of these keys are in no existing switcher**, because they are new in the
   3.x "glass" builds: `cachedScopedProfile` and `stripeSubscriptionStatus`. Had
   the ecosystem's five-key list been written in from guesswork, a switch would
   have left the previous account's display name in the account menu and its
   subscription status beside the new account's token.

### `glass.lastSignedInAuthId` — a widening, stated out loud

This key sits **outside** the `cursorAuth/` prefix that section 4 named as the
whole claim. It is owned anyway: the sign-in wrote it, and it holds the same
identity the token does - the JWT's `sub` claim verbatim. Left alone, a switch
would leave Cursor holding account B's token beside account A's id, which is not
a state any measurement observed Cursor in. It is one key, named in full, and it
is the only one outside the prefix.

The identity is read from the token's `sub` rather than rebuilt as
`auth0|<user_id>`. The two agree for every account measured, but `sub` is a copy
and the other is an assumption about the provider prefix, so the copy goes first
and the assumption is the fallback.

### Adopting the signed-in session — the rule the measurement changed twice

`Api._adopt_live_session` exists so a switch cannot throw away a session the user
has no other copy of. Two things about it were wrong until the code met a real
machine:

1. **It ran the stored values through the paste parser**, on the theory that one
   of the keys would hold a cookie. None of them does - the token sits bare in
   `accessToken` and the identity is a separate row - so it found nothing on every
   start. It now assembles the account from the named keys, via
   `switch.live_account()`, which is the exact inverse of `_auth_values` and lives
   beside it so a key that moves has to move twice on one screen.
2. **It only fired when the pool was empty.** Paste one cookie before U-Pool has
   ever seen the editor - the first thing anybody does - and the live session was
   never adopted, so the first `Use` would destroy it. That is the precise data
   loss the function exists to prevent, reintroduced by its own guard. The test is
   now whether that `user_id` is pooled. Add-only and keyed on the id, so it
   cannot duplicate a row or overwrite a token pasted for the same account.

The cost of (2) is that deleting the signed-in account brings it back next launch.
That is the right way round: a row deleted twice is a nuisance, a credential with
no other copy is gone.

### `cursorAuth/onboardingDate` — measured, deliberately not owned

The sign-in wrote it; U-Pool cannot produce it, because a pasted cookie carries no
onboarding date. Owning it would therefore mean blanking it on every switch, and a
blank onboarding date is how you ask Cursor to run onboarding again. Leaving the
previous account's date costs nothing. The narrower claim wins.

## 7. Storage — `~/.u-pool/cursor.json`

Plain text, `atomicio.write_json(..., secret=True)`, same protection as
`config.json`.

Separate from `config.json` rather than a section inside it, for two reasons:
`Store._normalise` rebuilds the document from `_empty()` and copies only `apps`,
so an unknown top-level section is silently dropped on every save; and the
account list has no `Provider` to normalise through. It follows the precedent of
`env-owned.json` and `codex-login.json` - U-Pool state that is not a provider
record gets its own file.

Encryption was offered and declined. Recorded here so it is not re-litigated:
these tokens are full account credentials, they sit in plain text, and anyone
with the file has the accounts. That is the same exposure `config.json` already
carries for provider API keys.

## 10. Out of scope, on purpose

- **Machine ID / telemetry reset.** Section 4.
- **Force-killing Cursor.** Section 5.
- **Writing the Electron cookie jar**, unless section 6 proves it is required.
- **Deleting Cursor transcripts.** `sessions.py`'s `TARGETS` table does not grow
  a Cursor entry; nothing here needs one, and a guessed path in that table is
  precisely what the table exists to prevent.
- **Token and cost tracking for Claude Code and Codex.** This was the other half
  of the original 0.8.0 request. It is a separate subsystem - parsing 117
  transcript files / 52.9 MB under `~/.claude/projects` and 3 files under
  `~/.codex/sessions` into per-day, per-model, per-project token and cost
  figures - with no code in common with the Cursor pool. Deferred to 0.9.0 so
  0.8.0 ships one thing. Note the tension to resolve there: 0.7.0's session
  purge deletes the very files a usage history would be computed from.

### One pre-existing bug, found by running it twice

`clis.refresh_async(force=False)` took `_lock` and then called `snapshot()`, which
takes the same **non-reentrant** lock. Cold, the branch is skipped and nothing
notices; warm, the process stops dead. Shipped in 0.7.0 and invisible because
`bootstrap` is the only `force=False` caller and normally runs once - but a
webview reload calls it again, and that hung the app with a blank window and
nothing in any log. Fixed by reading under the lock and answering outside it,
with a regression test that fails by timing out rather than by asserting.

- **A live round-trip, applied to the real install** with the author's say-so.
  Their own account was pooled, refreshed and switched to; the write went to
  `%APPDATA%\Cursor\...\state.vscdb` itself. Result: all eight owned keys
  **byte-identical** to what Cursor's own sign-in had written, `onboardingDate`
  untouched, 148 rows before and after, `state.vscdb.backup` beside the original.

  The first run of that was not byte-identical, and finding out why is what the
  round-trip was for: `cachedScopedProfile` came back as `{"displayName":…}` with
  the avatar dropped, because the design assumed a cookie carries no picture. The
  live `/api/auth/me` returns one - the very URL the blob already held - so
  `CursorAccount` gained an `avatar` field, `_identity` reads it, and the profile
  is written whole. The field is popped out of `summary()`: it exists to be
  written back into Cursor, not to put a remote image URL in front of the webview
  for a card that was never designed to show one.

### Not verified
