# U-Pool 0.9.0 — design

Two things ship in 0.9.0, and only one of them is new machinery:

1. **A token & cost panel** - a seventh tab that reads what Claude Code and Codex
   have already written to disk and reports, per day, per model and per project,
   how many tokens went out and roughly what they cost. This is the half of the
   original 0.8.0 request that was deferred (see the 0.8.0 spec, section 10).
2. **Official provider presets** - the ToS-compliant, official-key templates that
   were still missing from the catalogues: Anthropic and OpenAI's own APIs, plus
   Gemini, Groq, Mistral, Together, Fireworks and Venice. Data, not machinery.

What is **not** in 0.9.0, stated up front because it was asked for: turning a
`claude.ai` or `chatgpt.com` browser cookie into a local OpenAI-compatible proxy
API (a "sub2api"). That reuses a web subscription session as a programmatic API,
which both vendors' terms forbid and which gets the account closed. It also breaks
U-Pool's premise - *manage the credentials you own* - so it is refused, not
deferred. The same underlying wish (drive more than one Claude/OpenAI access from
one place) is met the honest way, by the official-API presets in part 2.

## Why

The panel answers a question the current app cannot: *where is the money going.*
U-Pool already knows which endpoint is live for each tool; it has never known what
that endpoint has cost. The data to answer it is already on the machine - every
Claude Code and Codex turn is logged with its token counts - so this is a reader,
not an instrumentation project. Nothing new is measured; what exists is summed.

## Scope

| # | Change |

| 3 | `parse_codex.py` - fold `~/.codex/sessions/**/rollout-*.jsonl`, attributing tokens to each turn's model |

## 0. Why this is a subsystem and not an adapter

The panel writes nothing to any CLI. An adapter's job is a surgical write into a
file another program reads; this reads two directories a CLI wrote and writes only
U-Pool's own snapshot under `~/.u-pool`. It shares no code path with `adapters/`
and no state with a `Provider`, exactly as `cursor/` shares none - so it gets its
own package, `src/upool/usage/`, rather than a seat in the adapter machinery.

The one seam it has into the rest of the app is a single call inside
`Api.delete_sessions` (section 4). That is deliberate and load-bearing, and it is
the only coupling.

## 1. `src/upool/usage/` — layout

```
src/upool/usage/
  __init__.py      # UsageService factory, the bucket dataclass, public surface
  models.py        # Bucket, Snapshot, FileMark - plain frozen dataclasses
  parse_claude.py  # one Claude transcript directory -> buckets
  parse_codex.py   # one Codex sessions tree -> buckets
  pricing.py       # built-in table + pricing.json overlay -> cost(model, tokens)
  store.py         # load/save ~/.u-pool/usage.json, merge new buckets in
  service.py       # rescan changed files, merge, return aggregates for the UI
```

The split mirrors `cursor/`: parsing, pricing, storage and orchestration are four
things a reader can hold separately, and the two parsers have nothing in common
but their output type, so they do not share a module.

## 2. What the transcripts actually contain — measured 2026-09-24

The design is built on the real files on the development machine, not on a guess
about the format. Both were read (never written) through ordinary `Read`.

### Claude Code — `~/.claude/projects/<dir>/<uuid>.jsonl`

The project directory name is a mangled absolute path (`C--Users-VECTOR-Desktop-…`).
Each line is a JSON object; the ones that carry cost are `type == "assistant"`:

```json
{
  "type": "assistant",
  "timestamp": "2026-09-10T19:18:51.820Z",
  "message": {
    "model": "claude-opus-5",
    "usage": {
      "input_tokens": 2,
      "output_tokens": 663,
      "cache_creation_input_tokens": 19824,
      "cache_read_input_tokens": 32547
    }
  }
}
```

So the four token counts, the model and a UTC timestamp are all on one line. The
project is taken from the transcript's own `cwd` field where a line carries one,
falling back to the demangled directory name - the directory name is lossy (a `-`
in a real folder name is indistinguishable from a path separator), the `cwd` field
is not.

### Codex — `~/.codex/sessions/**/rollout-*.jsonl`

Three line kinds matter, and the model is **not** on the token line:

- `session_meta` (first line): `payload.cwd` is the project; `payload.timestamp`
  dates the session; `payload.cli_version` is incidental.
- `turn_context`: `payload.model` - and it **changes within a session**. The
  development machine had sessions mixing `codex-auto-review` and `gpt-6-astra`.
- `event_msg` with `payload.type == "token_count"`: `payload.last_token_usage`
  holds this turn's `input_tokens`, `cached_input_tokens`, `cache_write_input_tokens`,
  `output_tokens`, `reasoning_output_tokens`. There is also a `total_token_usage`
  (cumulative) on the same line - **`last_token_usage` is summed, `total_token_usage`
  is ignored**, because summing the cumulative field double-counts every turn.

The parser therefore tracks "the model named by the most recent `turn_context`"
and attributes each `token_count` to it. A `token_count` before any `turn_context`
(should not happen, but is not impossible) is attributed to `session_meta`'s
provider-less model, recorded as the literal `"unknown"` so it is visible rather
than dropped.

### The token-kind mapping

The two formats name their cache tokens differently; the bucket normalises both to
four kinds, because cost depends on the distinction (cache-read is cheap,
cache-write is dear - collapsing them into "input" makes the dollar figure wrong):

| Bucket kind | Claude field | Codex field |
|---|---|---|
| `input` | `input_tokens` | `input_tokens` (minus cached, see note) |
| `output` | `output_tokens` | `output_tokens` + `reasoning_output_tokens` |
| `cache_read` | `cache_read_input_tokens` | `cached_input_tokens` |
| `cache_write` | `cache_creation_input_tokens` | `cache_write_input_tokens` |

Note on Codex `input_tokens`: Codex's `input_tokens` is measured to **include**
`cached_input_tokens` (the cached read is a subset of the input, not a sibling), so
the bucket stores `input = input_tokens - cached_input_tokens` to keep the four
kinds disjoint and the cost sum correct. Claude reports them as siblings, so no
subtraction there. This asymmetry is the kind of thing the tests pin (section 7);
if a future Codex build changes it, a test fails rather than the dollar figure
drifting silently.

## 3. The bucket, the snapshot, and incremental parsing

### The bucket

```python
@dataclass(frozen=True)
class Bucket:
    app: str        # APP_CLAUDE | APP_CODEX
    date: str       # "YYYY-MM-DD", local time (see below)
    model: str
    project: str    # a display name, the basename of the cwd
    # accumulated:
    messages: int
    input: int
    output: int
    cache_read: int
    cache_write: int
```

Buckets are keyed on `(app, date, model, project)` and summed. That is the finest
grain the UI slices on and the coarsest that still lets it answer "which project,
which model, which week."

**Date is local, computed at parse time.** The timestamps are UTC (`…Z`). A user
reads "today" as their day, not UTC's, so the parser converts once, when it reads
the line, and stores the local `YYYY-MM-DD`. This is settled at parse time on
purpose: the snapshot must not need re-bucketing if the machine's timezone
changes, and a turn is attributed to the day it happened in the user's zone.

### The snapshot — `~/.u-pool/usage.json`

```json
{
  "version": 1,
  "buckets": [ { "app": "...", "date": "...", "model": "...", "project": "...",
                 "messages": 0, "input": 0, "output": 0,
                 "cache_read": 0, "cache_write": 0 }, ... ],
  "files": { "<absolute path>": { "size": 12345, "mtime": 1690000000.0,
                                  "offset": 12000 } }
}
```

Two records in one file: the accumulated `buckets`, and a `files` map of parse
progress. `usage.json` lives under `app_home()` (`~/.u-pool`), so it is a different
tree from `~/.claude` and `~/.codex` entirely - which is what makes it survive a
session purge (section 4), and what makes the existing sandbox cover it for free
(section 7).

### Incremental parse

On a rescan the service walks every transcript file and, for each:

- **Unchanged** (`size` and `mtime` match the `files` map): skipped entirely.
- **Grown** (size larger, same file): seek to the stored `offset`, parse only the
  new bytes, add their buckets, update `offset`/`size`/`mtime`. JSONL sessions are
  append-only, so resuming from a byte offset reads exactly the lines not yet
  counted. The offset is advanced only to the end of the last **complete** line
  parsed - a half-flushed final line is left for the next pass.
- **Shrunk or replaced** (size smaller, or mtime older than recorded): treated as a
  new file - the old contribution cannot be cleanly subtracted, so its `files`
  entry is reset and it is parsed from zero. In practice this only happens if a
  file is truncated, which these CLIs do not do; the branch exists so a corrupt
  mark cannot wedge the parser.
- **Gone** (in the map, not on disk): its `files` entry is dropped, **its buckets
  are kept**. This is the purge case (section 4).

A file that fails to parse (bad JSON, unreadable) is counted in a `skipped` tally
returned to the UI and left out of `files`, so the next pass retries it - the same
"count what you skipped, never pretend you covered it" rule the Cursor importer
follows.

## 4. Surviving the session purge — the tension the 0.8.0 spec flagged

0.7.0's "delete all sessions" erases the very directories this panel reads. The
resolution has three parts, none of which touches `sessions.TARGETS`:

1. **Separate tree.** The snapshot is under `~/.u-pool`; `sessions.TARGETS` points
   only into `~/.claude` and `~/.codex`. The purge physically cannot reach it. No
   guard, no exclusion list - it is out of range by construction.

2. **Refresh before the purge.** `Api.delete_sessions(app)` calls
   `usage.refresh(app)` *before* it calls `sessions.purge(app)`. So every token up
   to the moment of deletion is folded into the snapshot first. This is the one
   coupling between the two subsystems, and it is one line. It is ordered, not
   parallel: the refresh must complete before the delete begins.

3. **Kept-on-gone.** When the rescan after the purge finds a file missing, it drops
   the file's progress mark but keeps its accumulated buckets (section 3). The
   history therefore shows the deleted sessions' totals; it just cannot attribute
   any *new* tokens to files that no longer exist.

The cost of this design, stated plainly: after a purge the panel's totals are
frozen snapshots, not re-derivable. If `usage.json` itself is deleted, the history
for already-purged sessions is gone for good - there is no second copy, the same
way `sessions.py` keeps no copy of what it deletes. That is acceptable: the
snapshot is a convenience over data the user chose to destroy, not a backup of it,
and the UI says so next to the purge buttons.

## 5. Pricing — `pricing.py`

Cost is the one figure not in the transcripts, so it comes from a table:

```python
# $ per 1,000,000 tokens, by kind. None where a rate is unknown.
BUILTIN: dict[str, dict[str, float]] = {
    "claude-opus-5":   {"input": 15.0, "output": 75.0, "cache_read": 1.5,  "cache_write": 18.75},
    "claude-sonnet-5": {"input": 3.0,  "output": 15.0, "cache_read": 0.3,  "cache_write": 3.75},
    # ... the models actually seen, plus current OpenAI/Codex rates ...
}
```

- **Match by prefix.** A model id is matched against the longest table key that
  prefixes it, so `claude-opus-5-5` resolves through `claude-opus-5`. An exact key
  wins over a prefix.
- **Overlay.** `~/.u-pool/pricing.json` is read on top of `BUILTIN`, key by key, so
  a user can correct a rate or add a custom relay's model without editing code. Its
  shape is the same dict; a partial entry (only `output`, say) overlays only that
  kind.
- **Unknown → `None`.** A model with no rate for a kind contributes `None` to that
  kind's cost. The bucket's cost is the sum of the known kinds; if the model is
  entirely unpriced the cost renders as `—` while the token counts still show.
  Cost is never silently zero - zero would read as "free," `—` reads as "unknown."

The exact built-in numbers are filled from each vendor's public pricing page during
implementation and dated in a comment, because they change; the *structure* is what
this spec fixes, not the cents.

## 6. UI — the Usage tab

A seventh tab, read-only, following the existing card/panel visual language.

- **Tiles** across the top: total cost and total tokens, for *this month* and *all
  time*, split Claude vs Codex. A tile whose cost is unknown shows tokens and a `—`
  for dollars.
- **Daily series**: a bar/area chart of cost (toggle: tokens) per day over the
  selected range. Built per the `dataviz` skill - accessible in both themes, the
  neutral palette swapped for U-Pool's blues.
- **Breakdown table**: rows by model and, on a toggle, by project. Columns: the
  four token kinds, total tokens, cost. Sortable. This is where the cache-read vs
  cache-write split earns its place - it is visible here.
- **Range selector**: last 7 days / 30 days / all.
- A **Refresh** button and a quiet "as of <time>" so a stale panel is obvious.
- CSV export is **out of scope** for 0.9.0 (YAGNI); the breakdown is on screen.

Settings gains a **Pricing** subsection: a small editable table over the merged
built-in+override rates, saving to `pricing.json`, plus an "open file" button for
hand edits - the same pattern as the environment panel's "open editor."

The bridge surface (all `@endpoint`, `{ok,data}` envelope, no secrets - there are
none here anyway):

- `usage_summary(range: str) -> {tiles, series, breakdown, as_of, skipped}`
- `usage_refresh() -> {ok...}` (rescan + merge, returns fresh summary)
- `get_pricing() -> {builtin, overrides, merged}`
- `set_pricing(overrides: dict) -> {ok...}`

## 7. Tests and the sandbox

**No new write target leaves the home directory.** `usage.json` and `pricing.json`
are under `app_home()`, which the sandbox already redirects via `UPOOL_HOME`; the
transcripts read are under `home()`, already redirected via `UPOOL_FAKE_HOME`. So
unlike Cursor, 0.9.0 adds **nothing** to `conftest.py`'s redirect list - and the
spec says so explicitly so a reviewer can confirm the "if you add a write target,
redirect it" rule in CLAUDE.md is not being skipped, it simply does not apply.

Tests, over tiny hand-written transcript fixtures:

- **Claude parse**: the four token kinds land in the right bucket kinds; model and
  local date are correct; a non-assistant line is ignored.
- **Codex parse**: `last_token_usage` is summed and `total_token_usage` ignored;
  tokens follow the *current* `turn_context` model across an in-session model
  change; the `input = input - cached` subtraction holds.
- **Incremental resume**: parse a file, append lines, reparse - only the new lines
  are counted, offset advances, totals are the same as a from-scratch parse.
- **Purge survival**: parse, snapshot, delete the source directory, reparse - the
  buckets remain, the `files` marks are dropped, no new tokens are attributed.
- **delete_sessions ordering**: a spy proves `usage.refresh` runs before
  `sessions.purge` and that the post-purge snapshot includes the pre-purge turns.
- **Pricing**: prefix match, exact-over-prefix, override overlay (full and partial),
  unknown model → `None` cost with token counts intact.

## 8. Official provider presets

Data added to `ui/lib/presets.ts`, one entry per tool catalogue that supports the
endpoint. These are the ToS-compliant, official-key templates that were missing:

| Preset | Claude Code | Codex | OpenCode | Note |
|---|---|---|---|---|
| Anthropic (official API) | ✓ | — | ✓ | `api.anthropic.com`, `ANTHROPIC_API_KEY`, current models |
| OpenAI (official API) | — | ✓ | ✓ | `api.openai.com`, `OPENAI_API_KEY` |
| Google Gemini | — | ✓ | ✓ | OpenAI-compatible endpoint |
| Groq | — | ✓ | ✓ | OpenAI-compatible |
| Mistral | — | ✓ | ✓ | OpenAI-compatible |
| Together | — | ✓ | ✓ | OpenAI-compatible |
| Fireworks | — | ✓ | ✓ | OpenAI-compatible |
| Venice | — | ✓ | ✓ | OpenAI-compatible (`api.venice.ai`) |

Claude Code only receives Anthropic-compatible presets; the OpenAI-shaped ones go
to the Codex and OpenCode catalogues, whose config already speaks that shape. This
is a data change with no adapter change - the machinery to write each of these
already exists; only the templates were absent. OpenRouter already ships as a
preset and is simply present in more catalogues.

**Brand marks needed** in `ui/public/brands/`: `groq`, `mistral`, `together`,
`fireworks`, `venice`. `google` (Gemini), `anthropic` and `openai` already exist.
Each new mark is the vendor's own SVG logo, sized to match the existing set.

## 9. Out of scope, on purpose

- **The cookie→proxy "sub2api".** Refused, not deferred - see the top of this
  document. It violates the vendors' terms and U-Pool's own premise.
- **Cursor in the panel.** Cursor's usage is a request quota / plan figure of a
  different shape, already shown on its own card from `/api/usage-summary`. Folding
  it into a token-and-dollar panel would mean reconciling two incompatible units;
  the panel is Claude Code and Codex only.
- **CSV / JSON export.** Section 6. On screen is enough for 0.9.0.
- **Editing or trimming transcripts from the panel.** It reads; it never writes to
  a CLI's files. The only destructive session action stays in `sessions.py`.
- **Live/streaming counts.** The panel reflects what is on disk at refresh time,
  not a running total of an in-flight session.

## Verification

Filled in during implementation, following the house pattern (the 0.8.0 spec's
section 6): the parsers run against the real `~/.claude/projects` and
`~/.codex/sessions` on the development machine - read-only - and their totals are
checked against a hand count of a small file and against Codex's own final
`total_token_usage` for a single-model session (where cumulative and summed must
agree). Any figure that cannot be checked against a second source is called out
rather than asserted.
